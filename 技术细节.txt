========================================================
  Wallpaper Engine 解包工具  ·  技术细节
========================================================

日常使用请看「使用说明.txt」。本文件记录原理、实测数据
和已知限制，想深究的时候再看。


【一、实测覆盖情况】

在真实的 Steam 创意工坊订阅上验证（Wallpaper Engine 的
appid 是 431960），共 15 个包、297 MB：

   PKG 解包      15 / 15 个包全部成功
                 覆盖 PKGV0009 / 0010 / 0013 / 0016 /
                 0018 / 0021 / 0022 / 0024 八个版本
                 最大 129 个条目 / 128 MB

   TEX 提图      43 / 70 张无损提取（37 PNG + 6 JPEG）

此外还测过这些边界情况，全部通过：

   路径带空格                路径带括号 (2)
   路径带 !                  目录带尾随反斜杠
   目录不带尾随反斜杠         一次拖多个文件
   无参数启动（显示用法）

PKG 解析的正确性判据是「字节级闭环」：条目表结束位置加上
数据区长度，必须精确等于文件大小，而且数据区必须从 0 开始
没有空洞。任何解析错误都会立刻被这个判据抓住，不会静默
产出垃圾文件。


【二、PKG 格式的关键点】

文件开头：

   int32 magicLen | "PKGV0024" | int32 <未知>

条目记录，重复到文件末尾：

   int32 nameLen | name | int32 offset | int32 size

三个容易踩坑的地方：

 1. 版本号是魔数的一部分（PKGV0024 就是 v24）。紧跟其后
    的那个 int32 不是版本号。

 2. 没有独立的「条目数」字段。偏移 16 处的值就是第一条
    记录的 nameLen。

 3. offset 是相对「条目表结束位置」的，不是相对文件开头。
    记录里没有 NUL 填充，也没有额外的保留字段。

因为不同版本存在细节差异，pkg.mjs 没有写死单一布局：
它会枚举几种变体（名字是否带 NUL、是否 4 字节对齐、是否
有额外字段），只接受能精确闭环的那一个，并优先选择解析
出条目最多的方案。


【三、TEX 格式的关键点】

1. imageFormat 字段不可信

   这是最反直觉的一点。大量纹理的 imageFormat 标称
   13（DXT1）或 2（DXT5），但载荷其实是一张完整的
   PNG 或 JPEG。

   所以正确做法是先按字节签名判断，只有找不到图片签名
   时才走 DXT 解码：

      载荷以 89 50 4E 47 开头  ->  内嵌 PNG
      载荷以 FF D8 FF 开头     ->  内嵌 JPEG

   这样提取是无损的，字节原样取出，不经过任何解码或重编
   码。（用 RePKG 之类的工具反而会把它解成 DXT 再转存，
   白白掉一次画质。）

2. TEXI 里有两个尺寸，别搞混

      texW / texH  =  显存对齐后的尺寸，例如 4096x4096
      imgW / imgH  =  真实图像尺寸，  例如 3840x2160

   两者经常不一致。取图请以图片自身的头部为准。

3. mipmap 链是逐级内嵌的完整图片

   图像数据后面跟着降采样层级，每一级各自是一张完整的
   PNG 或 JPEG：

      TEXB0003: flags | imageFormat | mipCount |
                width | height | 0 | 0
      然后逐级: [宽][高][0][0][长度] + <内嵌图片>
                （尺寸逐级减半）

   例如某个 7 级纹理：
      3840x2160 -> 1920x1080 -> 960x540 -> ... -> 60x33

   注意容器的 mipCount 也不可靠（见过声明 7 级但实际只
   存了 2 级的），所以解析器是「数据驱动」的：一直读到
   无法构成合法记录为止，而不是按 mipCount 循环。


【四、已知限制】

70 个纹理里有 27 个提取不出图片，全部是
imageFormat = -1 的 LZ4 压缩遮罩纹理（水波、抖动、光晕
等特效用的灰度图，不是壁纸本体）。

这类是 LZ4 压缩的 RGBA 像素数据，不是内嵌图片。其中 19 个
已经能正确识别框架（rawSize == storedSize 时按未压缩处理，
否则按 LZ4 解压），但剩下 8 个的多级 mip 链，数据起始位置
在不同文件之间不一致（实测 p+8 和 p+12 两种情况都有），
尚未找到统一规律，因此暂未支持。

对「提取壁纸」这个目的没有影响 —— 壁纸本体都是内嵌的
PNG / JPEG，全部能正常提取。


【五、运行环境】

Node.js 即可，只用内置的 fs / path / zlib 模块，
无任何外部依赖。

不需要 .NET SDK、不需要联网、不需要管理员权限。


【六、关于 run.bat 的两条硬约束】

这两条是踩坑踩出来的，不要「顺手简化」掉：

 1. 批处理里只能放英文（纯 ASCII）。
    含中文的 .bat 存成 UTF-8 后，cmd.exe 会按 GBK 去读，
    脚本还没开始执行就已经解析失败了。

 2. 所有 node 调用都要加 call。
    这台机器上的 node 实际是个 .cmd 转发脚本，从 .bat 里
    运行另一个 .cmd 而不加 call，控制权交出去就再也回不来，
    脚本会在那一行直接终止。

另外注意别开 enabledelayedexpansion，它会让 cmd 吞掉路径
里的感叹号。
